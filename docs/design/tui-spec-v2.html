The journey the whole interface is one path

The audit's journey test stuck at doctor, verify, and receipt detail — three of the seven steps. A first-time user can't tell what Timmy is for because no screen shows the loop. So the interface is organized around one loop, and Home shows where you are in it.

  STEP   VERB                   PROOF IT HAPPENED            WHERE
  1      timmy doctor           doctor.pass receipt          HOME  (status strip)
  2      timmy connect <tool>   env.lock receipt             LIBRARY › fleet
  3      timmy run <lane>       lane.start → live pane       RUN
  4      (receipt lands)        rc_… sealed, prev → this     RUN → CHAIN
  5      timmy verify           chain ok · N  (glows)        CHAIN
  6      companion QR           companion.pair receipt       HOME  (QR chip)
  7      timmy seal <anything>  your first receipt           anywhere

  ▶ Home lights the NEXT unsealed step in orange. Everything else in the app is a variation of these seven.
    journey.first is sealed when all seven have a receipt — onboarding, metric, and demo in one receipt.
AUDIT FINDINGS THIS ANSWERS
  • Journey stuck at doctor (no in-TUI path) → step 1 is a Home action
  • Stuck at verify (C1, fixed) and receipt detail (C2, fixed) → steps 4–5 have one screen
  • "~12–14 keystrokes" → target ≤ 8 with which-key
RULES
  • Every step has a verb, a receipt kind, and a home screen. No step without a receipt.
  • The next step is the only orange thing on Home.
  • Steps never hide: a completed step shows its receipt hash, not a checkmark.

Information architecture nine tabs become four

COMMAND · MISSION · TELEMETRY · ESCROW · LANES · LIBRARY · PROJECTS · SYSTEM · REVIEW is a list of code modules, not a list of things a person does. Four tabs, named for verbs the journey uses.

new tababsorbswhat it answerskey
HOMECOMMAND, MISSION (current), SYSTEM (status)Where am I in the loop? What's connected? What just happened?1
RUNLANES, TELEMETRY, ESCROW, hot-drop intakeWhat is Timmy doing right now? What needs my approval?2
CHAINreceipts, verify, REVIEW, refusalsWhat happened, provably? Can I trust it?3
LIBRARYfleet/connectors, boards (mission/blueprint/template), PROJECTS, models registryWhat can Timmy use? What have I built?4
DOCTOR

timmy doctor is not a tab. It is the status strip on Home (one line, always visible) and a full report on demand via :doctor. SYSTEM as a destination goes away.

SOVEREIGN CHAT

Chat is a mode, not a tab. c from anywhere opens the chat drawer over the current screen; Esc closes it. The screen underneath stays visible, dimmed (fixes W1's bleed-through pattern globally).

Modes & keybinding scopes the footer is the source of truth

The digit-key bug and W5/W6 are one bug: keys had no scope. Neovim solved this forty years ago — a key means one thing per mode, and the mode is always on screen. The footer already prints MODE; now the mode owns the keymap.

MODE      what keys mean                                                   enter          leave
 NORMAL   1–4 switch tab · j/k move · Enter open · Esc back · ? which-key   Esc (default)   —
 INSERT   everything is text; only Esc and Tab are global               i  or  :        Esc
 CHAT     everything is text to the sovereign agent; Enter sends        c               Esc

SINGLE-MEANING KEYS (fixes W6 overload)
  Enter  = open the selected thing        Esc  = back / leave mode        Tab  = next pane in this tab
  /      = filter the current list        :    = command line (INSERT)    ?    = which-key overlay
  s      = seal (with confirm)            v    = verify chain             r    = refuse (RUN, needs reason)

FOOTER (always)
  NORMAL  HOME › status   [1-4] tab  [j/k] move  [Enter] open  [?] keys  [c] chat  [:] cmd              chain ✓ 724  bus ●

FOOTER IN INSERT / CHAT
  CHAT    sovereign · gemini-3.7-flash   [Enter] send  [Esc] leave  digits are text                          chain ✓ 724  bus ●
TEST (keyboard contract)
  • In INSERT/CHAT, send "23456" → input value is "23456", tab unchanged.
  • In NORMAL, send "3" → CHAIN tab.
  • Enter never triggers two actions; Esc never triggers zero.
  • Footer hint text is generated from the active keymap, never hand-typed (same lesson as the chip).

FIXES
  • W4 latency: the running lane has a progress bar and a spinner that ticks from the bus, never from a 3s poll. Anything >400ms shows motion.
  • Escrow was a tab nobody visited; now it's the pane that says "needs you" and appears only when something does.

  • Escrow: one item at a time, cost estimate always shown, requester receipt id always shown.

FIXES
  • C1 (fixed): status column derives from chain verify. OK sealed · — unverified · FAIL refused. Nothing else.
  • C2 (fixed): Enter opens the detail pane; it is always visible, so "how do I inspect?" never arises.

SPEC

  • Review notes (director/approver) render as receipts of kind review.note — no separate tab.

PICKER PROBLEMS SOLVED
  • Model ids meant nothing → role, context, price, caps, and real spend from receipts on one row.
  • Nobody knew which model the tmux harnesses ran → fleet rows show harness → policy model or → openrouter, from harness.policy.
  • Sparks are a free judge tier, visibly.
SPEC
  • Rows come from timmy models --json (models.registry): id, role, ctx, price, supported_parameters → caps, spend, notes, pinned.
  • Group by role with role ▾; fuzzy filter on /; pinned float to top.
  • [h] opens a sub-picker: which harness gets this model (opencode, jcode, pi, hermes). Writes harness.policy.
  • Fleet: ● connected, ○ not configured (dim — not red; absence is not failure).

Color contract a gate, not a style guide

The audit's worst finding wasn't a bug in a screen — it was the danger color spent on things that weren't dangerous (valid receipts, docker being off). When red is cheap, nobody believes it. The contract is enforced by a test with the audit's own view4 capture as the negative control.

colormeansmay appear onnever on
phosphor #33FF66the chain agreessealed/verified receipts, connected fleet, live bus, "chain ok", completed journey stepsanything unverified, any human input, any state the chain hasn't confirmed
orange #FF8C1Aa human is here / neededthe ONE next step, running lanes (you're waiting), escrow items, INSERT/CHAT mode badge, filter textmore than one element per screen (except RUN, where running lanes may be several)
red #FF3B3Brefusedrefused receipts, failed verification, tamper=BROKEN, refused escrowdocker off · missing keys · unconfigured connectors · empty states · warnings
dimabsent, off, unverified, secondaryeverything that is not one of the above—
white boldthe thing you are looking atselected row title, header wordmarkstatus of any kind
ROSTER GATE: tui.color-contract (kind=count)
  • Render every tab against fixture states: verified chain, refused receipt, running lane, docker off, missing key, unverified receipt, INSERT mode.
  • Assert: red cells appear only in refused/failed fixtures; orange count ≤ 1 outside RUN; phosphor only on chain-confirmed cells.
  • Negative control: /tmp/audit/view4.txt (pre-hotfix) must FAIL. Seal gate.control before admitting.

For Qwen implementation order and constraints

ORDER OF WORK
  • 1. Keymap + modes. One keymap object per (mode, tab). Footer and which-key render from it. Keyboard-contract test.
  • 2. IA collapse. Four tabs; old views become panes inside them. Remove SYSTEM as a destination; :doctor + Home status strip.
  • 3. Color contract gate with the view4 negative control. Admit to roster.
  • 4. HOME (journey, status, rails). journey.first seal when 7/7.
  • 5. CHAIN (list + fixed detail pane + verify strip).
  • 6. RUN (lanes from bus, live pane, drops, escrow-when-needed).
  • 7. LIBRARY (fleet, models picker from models.registry, boards, projects).
  • 8. Chat drawer over any screen; LanesPanel legacy write → bus.
CONSTRAINTS
  • Tokens from design/tokens.json product mode; seal design.lock first. No other colors, no other fonts.
  • Reference grid 120×32; must degrade to 80×24 by dropping the right rail, never by truncating rows mid-glyph.
  • Every status glyph comes from the bus or the chain — never from a poll, never hand-typed.
  • Any receipt row renders only fields the receipt schema has (CUE schema for receipts, typechecked in the renderer).
  • Reconcile each screen against your own captures in docs/ux-audit-bundle.md; where this spec and the captures disagree on a fact (a real field name, a real keybinding), the capture wins and you report it.
  • Seal ui.redesign per step, citing ui.audit 3f6b191b6. Before/after captures on each.
